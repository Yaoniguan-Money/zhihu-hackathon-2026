# 证据链狼人杀

> 产品定义 · 技术栈 · 双人分工 · 开发流程 · 数据接口  
> 开发基线文档 v2.0

> **核心命题** 所有人说的词和素材都来自原文，但只有一部分叙述保持原意；篡改者通过断章取义、范围扩大、因果偷换、时间蒙太奇、条件删除等方式，把“真的材料”拼成“原文不支持的意思”。玩家要找出的不是谁在胡编，而是谁偷偷改变了词与词、事实与事实之间的关系。

| **项目**     | **定义**                                                      |
|--------------|---------------------------------------------------------------|

# 一、产品定义

## 1.1 一句话定位

玩家输入知乎文章链接或选择系统案件，AI 将同一篇原文拆成事实链并生成多个角色。忠实角色只能表达“原文能够支持、逻辑能够成立”的内容；篡改角色不能凭空编造，只能利用原文已有素材，通过春秋笔法或蒙太奇式重组改变原意。玩家通过审讯、录音回放、角色互咬和证据拼图，找出信息在哪一步被偷偷改掉。

## 1.2 产品核心规则

| **规则** | **定义**                                                                                                 |
|----------|----------------------------------------------------------------------------------------------------------|
| 忠实角色 | 允许转述、摘要、有效推论；所有事实性表达必须被原文 Evidence Graph 支持。                                 |
| 篡改角色 | 所有词句都必须能追溯到原文素材，但允许删除条件、扩大范围、拼接时序、偷换因果等，形成原文不支持的新意思。 |
| GM       | 掌握完整原文事实图谱、角色身份、篡改算子和标准答案；不参与普通聊天。                                     |
| 玩家     | 不只是猜人，最终必须提交“篡改者 + 篡改方式 + 支撑证据”。                                                 |
| 验证     | 任何角色输出先经 Validator；忠实角色不满足 entailment 时必须重写，不能直接展示。                         |

## 1.3 什么算“正确”与“篡改”

| **表达类型** | **示例**                                                     | **是否合法** |
|--------------|--------------------------------------------------------------|--------------|
| 原文转述     | “三个部门进行了 AI 客服试点。” → “AI 客服先在三个部门测试。” | 忠实角色允许 |
| 有效推论     | “测试期人工处理量下降 18%。” → “试点期间人工压力有所下降。”  | 忠实角色允许 |
| 范围扩大     | “三个部门试点” → “公司已经全面使用”                          | 篡改         |
| 条件删除     | “在测试期间有效” → “长期有效”                                | 篡改         |
| 因果偷换     | “引入 AI 后指标上升，但原因未确定” → “AI 导致指标上升”       | 篡改         |
| 时间蒙太奇   | 2024 的增长 + 2025 的 AI 上线 → “AI 上线后增长”              | 篡改         |
| 上下文删除   | 只保留正向数据，删除作者对样本不足的限定                     | 篡改         |

## 1.4 篡改算子

| **distortion_type** | **含义**                              |
|---------------------|---------------------------------------|
| scope_expand        | 局部 → 整体；个别 → 普遍              |
| degree_strengthen   | 可能 → 一定；影响 → 决定              |
| condition_delete    | 删除“在某条件下 / 某范围内”等限定     |
| causal_swap         | 相关 / 同时发生 → 直接因果            |
| time_montage        | 把不同时间的事实拼成错误先后关系      |
| source_splice       | 拼接不同段落 / 不同人的表达形成新结论 |
| context_omit        | 删除会显著改变结论的上下文            |
| subject_swap        | 偷换主体 / 指代对象                   |
| concept_shift       | 用相近概念替换原概念                  |
| cherry_pick         | 只取支持某结论的材料，隐藏反例        |

## 1.5 Evidence Graph：产品真正的内容底座

```text
知乎原文 / 系统文章
↓
Article Parser
↓
段落 / 引用 / 数据 / 人物 / 时间
↓
Claim 原子事实
↓
Relations
├─ supports
├─ qualifies
├─ contradicts
├─ causes?
├─ temporal_before / after
└─ source_of
↓
Evidence Graph
```

- Claim 不是一整段摘要，而是最小可验证事实单元。
- 每个 Claim 必须保留 source_span，能回到原文具体文本。
- 忠实角色的 speech 必须能映射到一个或多个 Claim，并通过 entailment 校验。
- 篡改角色的 speech 也要引用 Claim，但 Validator 应识别其 distortion_type，而不是判为“凭空幻觉”。

## 1.6 角色体系

| **层**         | **公开/隐藏** | **作用**                                           |
|----------------|---------------|----------------------------------------------------|
| Persona        | 公开          | 陈教授 / 小林 / 老王等表达风格，只决定“怎么说”。   |
| Fidelity       | 隐藏          | faithful / distorted，只决定“内容是否忠实原意”。   |
| Visible Claims | 隐藏          | 每个角色能看到哪些事实。                           |
| Goal           | 隐藏          | 角色希望维护的立场、保护的信息、对其他角色的关系。 |
| Voice          | 公开          | TTS 音色与说话节奏。                               |

> **关键设计** 角色人格和真假必须彻底分离。同一个“陈教授”在不同案件里可以是忠实角色，也可以是篡改角色，避免玩家凭人设猜身份。

## 1.7 一局产品流程

| **阶段**     | **玩家体验**                             | **后台行为**                                        |
|--------------|------------------------------------------|-----------------------------------------------------|
| 1 案件生成   | 粘贴知乎链接 / 选系统案件                | 抓取正文 → Evidence Graph → Golden Truth → 分配角色 |
| 2 入场       | 阅读背景，看到 5 个角色                  | 只下发 CasePublic，不泄露 truth / fidelity          |
| 3 初轮陈述   | 5 人分别说明自己看到的情况               | Role Agent 仅获得自身 visible_claims                |
| 4 审讯       | 玩家打字或语音追问，可温和 / 直接 / 施压 | RoleResponse → Validator → 通过后流式展示           |
| 5 角色互咬   | 角色指出他人时间 / 范围 / 因果矛盾       | 引用 message_id + claim_id 生成 rebuttal            |
| 6 录音证据   | 保存某角色关键发言，播放给其他角色       | 生成 quote evidence 并触发 presentRecording         |
| 7 证据链拼图 | 拖动原始事实 / 角色转述 / 冲突点         | 保存 BoardState，计算冲突关系                       |
| 8 最终指控   | 提交人、篡改方式、证据链                 | GM 用 truth 评估                                    |
| 9 揭晓       | 看原文、角色转述和被偷换的具体部分       | 生成 RevealResult + Reality Mapping                 |

## 1.8 页面结构

| **页面** | **必须包含**                                              |
|----------|-----------------------------------------------------------|
| 案件入口 | 链接输入、系统案件、主题、开始按钮                        |
| 案件背景 | 摘要、人物、规则；不展示完整答案                          |
| 审讯桌   | 角色席位、当前发言、提问方式、文字/语音输入、原文档案入口 |
| 证据库   | 保存的角色发言、原文片段、claim 关联                      |
| 拼图板   | 原始事实 / 角色转述 / 玩家标记的偷换点                    |
| 最终指控 | suspect + distortion_type + evidence_ids                  |
| 揭晓     | 原文事实链、错误链、玩家证据、正确答案、现实映射          |
| 战绩卡   | 追问质量、证据完整度、语义辨别、分享                      |

## 2.4 Validator 必须独立存在

| **角色类型** | **Validator 行为**                                                                                          |
|--------------|-------------------------------------------------------------------------------------------------------------|
| faithful     | 检查 RoleResponse 是否被 support_claim_ids 完整蕴含；若出现范围扩大、条件删除、因果偷换等，拒绝并自动重写。 |
| distorted    | 允许 speech 不被原文整体蕴含，但要求组成材料来自指定 Claim，并且 distortion_types 必须属于本局配置。        |
| 任何角色     | 禁止出现 source graph 中不存在的新实体、数字、事件、来源。                                                  |

> **不能只靠 Prompt** “你一定不要胡说”不足以保证忠实角色正确。角色生成与 Validator 必须分两步；忠实角色只有 validate=entailed 才能发给玩家。

# 三、数据接口定义

## 3.1 接口总原则

- 浏览器永远只拿 Public 数据；truth、fidelity、distortion policy、hidden claims 只存在服务端。
- 所有接口以 contracts/ 下的 TypeScript 类型为唯一真相。
- 所有写操作必须携带 client_action_id，实现幂等。
- AI 输出必须结构化 JSON，不能靠前端从自然语言猜状态。
- ASR 只是输入源；语音和键盘最终都调用同一个 submitQuestion 接口。

## 3.8 submitQuestion 服务端流程

1. 校验 Session 当前允许审讯，校验 role_id。

2. 保存玩家 Message 与 player_questioned GameEvent。

3. 服务端读取该角色的 RolePrivatePolicy，只组装 visible_claim_ids 对应内容。

4. 调用 Role Agent 生成 RoleResponse。

5. 调用 Validator；faithful 未通过 entailment 时自动重写，最多重试 2 次。

6. distorted 角色仅允许使用配置好的 distortion_types，不能新增未配置操纵方式。

7. 保存最终角色 Message、ValidationResult（服务端私有）、GameEvent、Evidence unlock。

8. Convex realtime 推送到前端，前端再触发 TTS。

# 四、双人技术分工

## 4.1 分工方式

> **不要简单拆成前端 / 后端** 两个人按产品的两套核心系统拆：A 负责 Evidence / AI Engine，确保“说什么、为什么对/错”；B 负责 Game / Interaction Client，确保“玩家怎么审、怎么拼、怎么指控”。两边通过 contracts 和 Golden Case 联调。

| 发布验收     | 两个人分别在新浏览器完整打一局           |

# 五、开发流程

## 5.1 第一步：先做 Golden Case，不先写复杂页面

> **Golden Case** 选一篇真实知乎文章，人工做出第一份标准案件 case-demo-001.json。它必须包含 source、claims、relations、roles、truth、distortion、标准 evidence。两个人所有实现都先围绕这一个案件。

```text
case-demo-001/
source.md
case-public.json
claims.json
relations.json
role-policies.private.json
golden-answer.private.json
fixtures/
faithful-response.json
distorted-response.json
validation-result.json
reveal-result.json
```

## 5.2 并行开发顺序

| **阶段**         | **开发者 A**                                  | **开发者 B**                | **共同验收**         |
|------------------|-----------------------------------------------|-----------------------------|----------------------|
| 1 Contract 冻结  | 定义 Claim / RoleResponse / Evidence / Reveal | 用 fixtures 写页面 / XState | Mock 能完整打一局    |
| 2 Evidence Graph | 原文 → Claims / Relations                     | 案件入场 + 原文档案         | 能看到真实文章和角色 |
| 3 Role Engine    | Faithful / Distorted Generator                | 审讯 UI + Streaming         | 真实角色能回答       |
| 4 Validator      | 忠实重写、篡改分类                            | 错误 / retry / loading UI   | 忠实角色不越界       |
| 5 Evidence       | Evidence unlock / contradiction               | 录音 + 拼图板               | 证据链可操作         |
| 6 Final Judge    | GM Reveal                                     | 最终指控 / 揭晓页           | 完整第一局           |
| 7 Voice          | ASR/TTS Provider                              | 麦克风 / 播放器             | 语音输入与朗读       |
| 8 Polish         | 第二案件、稳定性                              | 战绩卡、动效、分享          | 比赛版本             |

## 5.3 两人接口协作规则

1. 所有接口先写 contracts，再实现；代码里不得存在“临时字段名”。

2. A 不等 B：AI 尚未完成时，B 使用 fixtures / Mock RoleResponse 完成完整 UI。

3. B 不等 A：页面尚未完成时，A 用最小调试页或测试脚本验证 Convex action 与 AI 输出。

4. 任何接口变更必须同步更新 fixture；fixture 就是可执行的接口文档。

5. 每次联调只解决一个垂直链路：submitQuestion → RoleResponse → Validator → Message → UI。

6. 文本链稳定后再接语音；语音不能改变业务接口。

## 5.6 最终验收

1. 从知乎链接或系统案件开始，能在 10–15 分钟内完整打一局。

2. 4 个忠实角色连续追问仍保持原文可支持；不出现无来源事实。

3. 篡改角色不凭空造事实，其错误可以明确归类到 distortion_type。

4. 至少一次角色互咬引用具体 message / claim，而非泛泛争论。

5. 录音与拼图最终能作为 FinalAccusation 的 evidence_ids 提交。

6. GM 揭晓明确展示“原文事实 → 角色转述 → 被修改的关系”。

7. ASR/TTS 故障时降级到文字，不阻塞游戏。

8. 刷新页面后能从 Session / Event 恢复当前局。

# 六、最终冻结版本

> **产品核心** 不是“AI 会不会说假话”，而是“当所有素材都是真的时，你还能不能发现意思已经被换掉”。

| **冻结项** | **最终选择**                                                  |
|------------|---------------------------------------------------------------|
| 玩法       | 5 角色 + GM；审讯 / 对质 / 录音 / 拼图 / 指控 / 揭晓          |
| 内容底座   | Evidence Graph：Claim + Relation + source_span                |
| 忠实角色   | 允许转述和有效推论；必须 entailment 通过                      |
| 篡改角色   | 只能重组原文事实；按 distortion_type 操纵关系                 |
| 关键 AI    | Role Generator + Validator + GM 三层分离                      |
| 技术栈     | Next.js + React + TypeScript + Bun + Convex + AI SDK + XState |
| 语音       | SenseVoice/FunASR + Kokoro-82M zh                             |
| 开发分工   | A：Evidence / AI Engine；B：Game / Interaction                |
| 协作基线   | Golden Case + contracts + fixtures                            |

v2.0 · 任何产品 / 技术修改优先更新 Golden Case 与 contracts，再改实现。
